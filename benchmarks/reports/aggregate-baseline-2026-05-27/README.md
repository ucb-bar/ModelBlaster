## What's in this bundle

- **`dashboard.csv`** — long format, one row per
  `(arm, workload, metric)`. 577 rows. Columns:
  `arm, workload, model, target, quant, runner, metric, value,
  stddev, n_runs, unit`. Easy to pivot in pandas / Excel.
- **`summary.md`** — pivot-table-style markdown, one section per
  workload split into `pre-kernel` and `kernel-synthesis` phases.
  Each metric shows `mean ± stddev (N=k)` across replicates.

## What this bundle does NOT cover

1. **FireSim cycles** for accelerator targets. Per `tmp/07_gotchas.md`
   #6, spike treats Gemmini / Saturn-OPU custom instructions as
   atomic (zero-cycle), so `cycles_spike` is functional-only on
   `rvv_opu`, `gemmini`, `hetero_gemmini_opu`. The dashboard records
   these but the aggregator flags them as non-authoritative in the
   `cycles_spike` row when target is in `ACCEL_TARGETS`. The real
   accelerator-cycle baseline needs a FireSim run.

2. **`gemmini_q31` numerics**. Spike's `libgemmini.so` is built with
   `acc_scale_t = float`. Our Q31 kernels emit Q0.31 int multipliers
   that get reinterpreted as float bits, producing `linf=9..72`
   verify failures. Cycle counts ARE captured but `verify_pass=false`
   on those cells. Real Q31 baseline needs a libgemmini built from
   `Q31GemminiRocketConfig` (chipyard-side rebuild outside this repo).

3. **`hetero_gemmini_opu`** verify on spike — `spike-hetero` works
   functionally (builds, runs, emits per-tile profile + xpurt_trace)
   but the accelerator-emulated outputs drift vs the PyTorch fp
   golden by linf=52. FireSim is the authoritative correctness +
   cycle capture for hetero.

4. **`cycles_spike` vs `wall_cycles.txt` semantics**. The metric the
   aggregator extracts is the sum of per-dispatch cycles from
   `profile_spike.csv` (total compute work). Each cell's
   `wall_cycles.txt` records the end-to-end inference cycles (a much
   smaller number on workloads with many dispatches). Both are
   tracked at the per-cell level but only `cycles_spike` appears in
   the dashboard. Adding a `wall_cycles_spike` metric that reads
   `wall_cycles.txt` would be a small follow-up; numbers in the
   per-cell methodology.md files cite the wall-cycle value.

## How to diff a future change against this baseline

```bash
# After making your compile-flow modification:
source scripts/setup_benchmark_env.sh
uv run mb-cost session start my-modification-2026-XX-YY \
    --label "My change: <one-line description>"
for spec in <workloads you want to measure>; do
    uv run python -m benchmarks.arms.arm_a_curated \
        --workload $spec --runs 3
    # or arm_b_bedrock for the LLM-driven matrix
done
uv run mb-cost session end
uv run python -m benchmarks.aggregate --runs 3

# diff against this baseline
diff -u benchmarks/reports/aggregate-baseline-2026-05-27/dashboard.csv \
        benchmarks/results/dashboard.csv | less

# or use mb-cost diff for a higher-level view per cost / kernel-source
uv run mb-cost diff benchmarks/reports/aggregate-baseline-2026-05-27 \
                    benchmarks/results
```
