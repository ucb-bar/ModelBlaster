# ModelBlaster baseline — 2026-05-28

Self-contained summary of the cycle baseline captured on the
GemminiAndOPUShuttleConfig FireSim bitstream
(`alveo_u250_firesim_shuttle_gemmini_opu`, build 2026-05-06). All
numbers are from arm A (curated kernels) unless noted otherwise.

Cycle units: `wall_cycles.txt` is mtime ticks. **Mtime semantics differ
across platforms** — on FireSim it tracks the target's mtime CSR
(~30 MHz effective on this build → 1 mtime tick ≈ 33 ns wall on the
emulated target); on spike (functional simulator) mtime advances
per-instruction-batch and is NOT a wall-clock cycle count. **Only
compare cells within the same platform.** Cross-platform ratios
(spike-scalar vs FireSim-gemmini) are NOT meaningful speedups. The
per-op `cycles` column in `profile_firesim.csv` is rdcycle (target
CPU clock @ 1 GHz).

## Within-platform speedups (the only valid comparisons)

**Spike (functional sim, same platform):**
- dronet: scalar 4,541k → rvv 276k = **16.5× RVV-over-scalar**
- yolov8n: scalar 104,405k → rvv 6,315k = **16.5× RVV-over-scalar**

**FireSim (cycle-accurate FPGA, same platform):**
- dronet: rvv_opu 295,424 → gemmini 18,620 = **15.9× gemmini-over-OPU**
- yolov8n: rvv_opu 6,911,827 → gemmini 2,831,550 = **2.4× gemmini-over-OPU**
- dronet hand-authored hetero (gemmini+OPU split) 18,206 ≈ pure-gemmini 18,620; OPU paths overlap gemmini so the chain doesn't pay extra.
- mlp_control: gemmini_q31 108 → gemmini 547 = **5.1× q31-over-int8** for tiny linear+ELU chain. rvv_opu identical to gemmini because both use the scalar reference kernel for the tiny shapes (no curated linear_s8 for small N).

**Do NOT compute spike-scalar / FireSim-gemmini** — different mtime
semantics; that ratio is not a real speedup. The earlier "243× over
scalar" figure crossed platforms and has been retracted. An honest
end-to-end "scalar → accelerator" multiplier would require scalar
measured on FireSim (not captured — would need a scalar.conf build
for the SoC).

## What's in the baseline bundle (artifacts per cell)

Each `benchmarks/results/A/<cell>/<run-id>/` directory holds:
- `wall_cycles.txt` — single integer mtime cycle count
- `accuracy.json` — linf, max_abs_err, max_rel_err, n_samples, bit_exact, verify_pass
- `profile_firesim.csv` — per-dispatch cycle breakdown (rdcycle)
- `cycles_per_op.json` — aggregated per-op cycles
- `kernel_picks.json` — which kernel variant was selected per op
- `passes_applied.json` — fusion / fold pass fire counts + sites
- `binary_size.json`, `graph_summary.json`
- `stage_timings.json` — extract / generate / build / run wall times
- `run.json` — schema_version, arm, workload_id, git_sha, started_at, wall_clock_s, peak_rss_mb, exit_status
- `env.txt`, `stdout.log`, `stderr.log`

Hetero cells additionally produce `xpurt_trace.csv` (per-dispatch core_kind + actual_start_cycles + actual_end_cycles) and `cross_tile_estimate.json` (static upper bound on inter-tile bytes).

## Schedulers wired

- `scripts/run_xpurt_scheduler.py` — bridge: profile CSV → XPU-RT MOSEK MIP → ModelBlaster schedule fixture. With `--solver MOSEK --time-limit 60` it solves the 30-dispatch dronet hetero schedule to optimum in < 1s. Constrains requantize-producing ops to one backend to dodge cross-backend numerical drift.
- `scripts/gen_3way_schedule.py` — topological 3-network layout for multi-job, multi-instance schedules. Output is directly compatible with `pipeline/ingest_xpurt_schedule.py`.

## Known issues (in `notes/known_issues.md`)

- **dronet × gemmini_q31** — bit_exact=False (linf=72). Q31 quantization vs PyTorch reference drift; deterministic, expected.
- **Cross-backend numerical drift** — convs/linears must stay on ONE backend per inference chain. Mixing gemmini and rvv_opu requantize policies on the same chain accumulates linf~52 error. Routing constraint is encoded in schedule fixtures and the MOSEK bridge (`infeasible_combinations`).
- **Zicbom not in bitstream** — `cbo.inval` traps illegal. Cache management would need bitstream rebuild with `WithAutoCounter` + Zicbom configs.
- **Autocounter probes absent** — no cache-miss / branch-mispred / memory-bandwidth telemetry today. Requires bitstream rebuild. Documented in `notes/observability_gaps.md`.
- **yolov8n × hetero** — not yet captured; the 3-way binary includes yolov8n's 212 dispatches but a yolov8n-only hetero (yolov8n_hetero_int8 workload row) is still pending schedule fixture work.

## Determinism

For FPGA-emulated cycles, all bit-exact cells show **identical** cycle counts across reps. The non-bit-exact Q31 cell also shows identical cycles (9,039) — the drift is in OUTPUT values, not in cycle count.

For arm B (Sonnet-driven kernel synthesis), cycles VARY across reps (16,004 vs 16,167 vs 14,195) because the LLM picks different kernel variants per attempt — the variation IS the signal we're measuring. Temperature schedule is logged in `run.json` (`llm_temperature_schedule: [0.0, 0.3]`, `llm_seed: null` — Bedrock doesn't expose seed).

## Scheduler self-instrumentation (xpurt SchedulerReport + postmortem)

The scheduler now emits a structured `SchedulerReport` per invocation
(see `xpu-rt/profiling.py`) covering: solver name/status, solve wall
time, makespan, per-resource utilization, dispatch-duration distribution
(p50/p90/p95/p99 + bucket counts), critical path, and cross-device
transitions. ModelBlaster auto-emits `scheduler_postmortem.json` per
FireSim hetero run, joining `xpurt_trace.csv` with the report on
dispatch_id and reporting unit-neutral prediction error.

Measured on `dronet_hetero_xpurt_mosek_int8` reps 2 & 3:
- **median_ratio (actual/predicted) = 0.001012** — confirms the
  bitstream's clock-domain ratio (predicted in rdcycle @ 1 GHz, actual
  in mtime @ 1 MHz → 1000:1).
- **RMS error vs median ratio: 4.46%**, p99: 5.89%, max: 21.0%
  (`sigmoid1` — tiny op where the mtime measurement has high relative
  noise).
- **makespan_predicted=18,182,341 rdcycle (~18.18 ms target time)**
  vs **makespan_actual=18,201 mtime (~18.20 ms target time)** —
  scheduler prediction within 0.1% of measured.

The xpurt library also exposes a solver-sweep CLI:

```bash
uv run python -m xpurt.bench --workload-script <fac.py> \\
    --solvers MOSEK,HIGHS --reps 3 --out /tmp/sweep.json
```

On the dronet 16-dispatch fused MIP, MOSEK and HIGHS both reach the
same optimum (makespan 16.272 ms); MOSEK runs 44–84 ms per solve,
HIGHS 40–47 ms. Both are well under the 60s time limit.

## Profile database — per-op cycle store

`benchmarks/profile_db.py` aggregates per-dispatch FireSim cycles from
all `profile_firesim.csv` files into a queryable JSONL store at
`benchmarks/profile_db/<network>__<target>__<quant>.jsonl`. Current
state after MOSEK/3-way captures:

- **48 (network, target, op_type) tuples present**, 3,138 dispatch
  records across 35 unique runs.
- **Determinism**: median across reps equals the latest-CSV cycles
  exactly (0% delta on every dispatch). FireSim emulation produces
  bit-identical timing across reps.
- **3 missing combos** (all mlp_control int8): `gemmini`, `gemmini_q31`,
  `rvv_opu`. Newly unblocked by the `elu_s8` reference kernel landing —
  Phase 1 gap-fill captures pending.

The XPU-RT scheduler bridge (`scripts/run_xpurt_scheduler.py`) reads

falling back to the legacy single-CSV path with `--cycles-source csv`.

## QRB5165 head-to-head (multi-network MOSEK / HEFT bridge)

The QRB5165 robotics reference (notes/figures/qrb5165_reference.png, source
tmp/image.png) shows 1 yolov8 + 2 dronet + 4 mlp_control packed into a
**75.71 ms** period on a 2-lane heterogeneous tile (CPU_P=Gemmini+scalar,
CPU_E=RVV+OPU). The prior naive 3-way generator (gen_3way_schedule.py)
laid out each network independently using single-network solo cycles and
under-predicted measured FireSim wall by ~33×.

A new bridge — **scripts/run_xpurt_scheduler_multi.py** — feeds all three
networks into ONE combined xpu-rt Workload (every dispatch of every
instance becomes an Operation), applies the cross-backend drift
constraint to keep conv2d_s8 / linear_s8 on the Gemmini tile, and lets
the xpurt schedulers registry pick the best schedule respecting tile
non-overlap + precedence. Solvers tried: MOSEK (fails past ~200 ops),
HEFT (clean, float-native, sub-ms accurate), CPSAT (sub-ms ops collapse
to 1 due to OR-Tools integer rounding — use HEFT instead).

| Bundle | Solver | Dispatches | Makespan | vs qrb5165 75.71 ms |
|---|---|---:|---:|---|
| **2 dronet + 4 mlp_control** (no yolo) | HEFT | 88 | **29.2 ms** | **2.6× faster** ✅ |
| 1 yolov8n@160 + 2 dronet + 4 mlp_control | HEFT | 300 | 419.3 ms | yolov8n@160 alone has 420 ms compute → near-optimal for our model size |

Every emitted fixture is post-solve validated for dep precedence + tile
non-overlap + cross-backend drift before being written. HEFT versions
have **0 violations**. CPSAT fixtures have integer-rounding artifacts
(documented as a known caveat; not used for measured runs).

The no-yolo head-to-head — same network mix qrb5165 shows running in
parallel on the same hetero hardware kind — packs into 29.2 ms predicted,
**2.6× faster than qrb5165 reports for that bundle**. Per-dispatch
predicted-vs-actual measurements via FireSim are in
benchmarks/results/A/3way_heft_*/<run-id>/ once the queued captures land.

For the full 1+2+4 bundle including yolov8n at 160×160 input (our
default), 419 ms is essentially the lower bound — yolov8n alone has
420 ms of single-network compute. Matching qrb5165's 75 ms with the
yolov8n included requires a smaller yolov8 variant (e.g. 64×64 input
≈ 67 ms compute); the extraction at 64×64 is ready in
examples/yolov8_nano_64/ but its int8 cycle profile is not yet
measured on FireSim.
